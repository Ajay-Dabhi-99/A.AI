# Generation API (image, video, audio)

**Image jobs: implemented in Phase 8, no provider enabled.** Video and audio: planned, Phase 9. Types: `packages/shared-types/src/attachments.ts`. Design: [ADR-015 §6](../decisions/ADR-015-vision-images.md).

| Method | Path                  | Access       | Success                     | Purpose                                     |
| ------ | --------------------- | ------------ | --------------------------- | ------------------------------------------- |
| GET    | `/api/image/status`   | Anyone       | `200 ImageGenerationStatus` | Whether image generation is offered, models |
| POST   | `/api/image/generate` | User         | `202 ImageJobResponse`      | Start an image job (`status: queued`)       |
| GET    | `/api/image/:id`      | User (owner) | `200 ImageJobResponse`      | Job status and, when completed, the image   |
| POST   | `/api/video/generate` | —            | planned (Phase 9)           | Start a video job                           |
| GET    | `/api/video/:id`      | —            | planned (Phase 9)           | Job status                                  |

## Current deployment state

No image provider is registered, so:

- `GET /api/image/status` returns `{ "enabled": false, "models": [] }`.
- `POST /api/image/generate` returns `503 MODEL_UNAVAILABLE` "Image generation is not enabled on this deployment." and creates no job.
- The web `/image` page says so. Nothing is advertised as available (blueprint §25).

## `POST /api/image/generate`

```json
{ "provider": "…", "model": "…", "prompt": "a red fox in the snow" }
```

`prompt` is trimmed, 1–2,000 characters. Unknown fields are rejected.

```json
{
  "job": {
    "id": "…",
    "status": "queued",
    "provider": "…",
    "model": "…",
    "prompt": "a red fox in the snow",
    "errorCode": null,
    "attachment": null,
    "createdAt": "…",
    "completedAt": null
  }
}
```

Poll `GET /api/image/:id` (the web app polls every 2 s) until `status` is `completed` (with `attachment`, `source: "generated"`) or `failed` (with `errorCode`). Show the image through `GET /api/attachments/:id/url`.

| Status | Code                | When                                           |
| ------ | ------------------- | ---------------------------------------------- |
| 401    | `AUTH_REQUIRED`     | Not signed in                                  |
| 404    | `NOT_FOUND`         | Job is not yours, or malformed id              |
| 429    | `RATE_LIMITED`      | More than 20 jobs in a day                     |
| 503    | `MODEL_UNAVAILABLE` | Generation not enabled, or unknown image model |

## How jobs run

- The `generation_jobs` row is the source of truth; progress is mirrored in Redis at `job:{jobId}` (1 hour).
- A job is claimed with a compare-and-set from `QUEUED` to `PROCESSING`, so only one API instance runs it.
- Each generation has a 120 s timeout (`PROVIDER_TIMEOUT`).
- The generated bytes are validated and stripped exactly like an upload; output that is not a supported image fails with `VALIDATION_ERROR`.

## Enabling a provider later

Implement `ImageGenerationProvider` (`packages/ai-core/src/image.ts`) in `packages/ai-providers` and register it in the API container (`imageProviders`). Storage must be configured. No route or UI change is needed.
